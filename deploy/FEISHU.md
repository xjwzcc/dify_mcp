# 飞书多维表格持久化试点

面向小组试用与故障验证，保留原 NAS 方案。使用中国版飞书企业自建应用，
服务端持 tenant_access_token 访问专用多维表格，师生不需要登录飞书。
不要把表格公开分享给学生，也不要直接编辑内部记录。

## 1. 创建多维表格与应用

1. 在 [飞书云文档](https://feishu.cn/drive/home/) 新建**多维表格**，命名为“教学系统存储验证”。
   建议新建独立 Base，不使用知识库内的现有教学资料。
2. 打开 [开发者后台](https://open.feishu.cn/app)，创建“企业自建应用”，例如“教学系统存储服务”。
   如果当前组织禁止成员自建应用，请联系飞书组织管理员开通或代建。
3. 应用内“凭证与基础信息”可取得 App ID 和 App Secret。
4. “权限管理”中申请 `bitable:app`（查看、评论、编辑和管理多维表格），
   在“版本管理与发布”创建版本并完成组织的发布/审核流程。此服务无需开通消息发送等无关权限。
5. 回到多维表格，通过右上角“…”中的“添加文档应用”（可能位于“更多”下）添加刚创建的应用，
   授予编辑权限。应用 API 权限和表格访问授权缺一不可。
6. 从表格 URL 的 `/base/` 后取得 app_token。例如
   `https://example.feishu.cn/base/bascnExample?table=tblExample` 的 app_token 是 `bascnExample`。
   不要把 App ID、app_token、table_id 混用；本项目初始化脚本会返回自己的 table_id。

官方参考：[多维表格常见问题及授权](https://open.feishu.cn/document/docs/bitable-v1/faq)、
[权限生效及文档授权说明](https://www.feishu.cn/content/137710114294)。
组织套餐决定配额与容量，需在实际租户核对，不能假定试点免费或无限量。

## 2. 本地配置与初始化

使用 Node.js 24，在仓库根目录：

```bash
cp deploy/feishu.env.example .env
chmod 600 .env
```

用本地编辑器填写 `.env` 的 App ID、App Secret 和 app_token。
`.env` 已加入 Git 忽略。不要把真实凭据贴到聊天、截图或提交到仓库。

然后运行一次：

```bash
node --env-file=.env scripts/init-feishu.cjs --create-test-tables
```

脚本会新建两个专用数据表，各含 `key`、`payload` 文本字段以及初始 head 记录，
输出以下四个非密钥配置，复制到 `.env`：

- `FEISHU_CATERING_TABLE_ID`、`FEISHU_CATERING_HEAD_ID`
- `FEISHU_HOTEL_TABLE_ID`、`FEISHU_HOTEL_HEAD_ID`

脚本不会清空现有表。若中途失败，保留已输出 ID，在飞书确认创建结果后再处理；
重复执行会创建新的表，不能将新建空表配置替换到已使用的系统中。
刚创建资源可能存在可见性延迟，需等资源可读后再启用。

生成一次 32 字节加密密钥并保存到 `FEISHU_STORAGE_KEY`，例如在本机执行 `openssl rand -hex 32`。
密钥必须独立安全备份并在重启、换实例及恢复时保持不变。丢失密钥将无法恢复数据。
再设置至少 8 位的 `TEACHER_PASSWORD`、`CATERING_CLASS_CODE`、`HOTEL_CLASS_CODE`；
已有账号不会因改变初始化密码而重置。

```bash
node --env-file=.env server.cjs
```

从统一入口进入师生端，先用少量测试账号进行保存、批阅、重启恢复。
同一组表只能有一个活动服务；本地验证结束须停止服务，再启动 FC。

## 3. FC 配置

仍使用 [部署说明](README.md) 的 ZIP、9000 端口及启动命令。
将 `.env` 对应项录入 FC 环境变量，密钥使用 FC 支持的安全配置方式：

| 配置 | 含义 |
| --- | --- |
| `STORAGE_BACKEND=feishu` | 选择飞书适配器 |
| `FEISHU_SINGLE_WRITER=1` | 确认已保证只有一个活动写入实例 |
| `FEISHU_APP_ID`、`FEISHU_APP_SECRET` | 自建应用凭据 |
| `FEISHU_APP_TOKEN` | 专用 Base 的 app_token |
| 两套 `TABLE_ID`、`HEAD_ID` | 初始化脚本输出的四个 ID |
| `FEISHU_STORAGE_KEY` | 固定的 64 位十六进制密钥 |
| 教师初始密码、两套注册口令 | 对应上节三个环境变量 |

飞书模式的 `DATA_DIR` 默认为 `/tmp/teaching-cache`，仅用于临时导出等文件；
权威数据在飞书，运行中的 SQLite 在内存中。正式版本不允许自定义飞书 API 地址，
只有测试环境支持本机模拟接口。

FC 最大实例数必须为 1；更新时停止旧版本后启动新版本，不允许多个版本、多个函数、
本地与云端同时写同一组表。环境变量不是锁；目前没有跨实例原子比较交换能力。
需要弹性扩容或多实例可用性时应更换数据库方案。
部署后验证 `/healthz` 的 `storage` 为 `feishu`，并实际执行登录、保存、重启和恢复。

## 4. 数据保存方式与边界

服务沿用两套应用的 SQL 模型，每次变更产生 SQLite changeset，压缩后经 AES-256-GCM 加密，
分片写入专用表，最后更新 head 指针并读回确认。只有确认完成才发送成功响应和实时通知。
每 25 次提交生成一个完整恢复快照，恢复只读取最近快照及之后的变更。
表中内容是内部日志，不是可直接手工修改的学生名册或成绩单。

请求在每套应用内排队；等待队列超过 100 会拒绝请求。接口显式限流可重试，
保存结果无法确认时返回 503 并停止后续读写，避免在旧状态上继续操作。
这时应保留页面、检查飞书权限/配额/网络、确保只有一个进程，再重启恢复，
通过重新查询记录判断上次操作是否已提交，不要盲目重复提交。
学校集中出口下的登录限流仍需结合实际课堂验证。

当前不自动删除历史日志，表格行数会持续增长；每个普通提交至少新增一个数据片和一个清单，
大状态或截图会产生更多分片。达到表格或 API 配额会停止保存，不会自动切换到本地临时盘。
不要手动删除不明记录；试点应监测行数、配额、P95 保存延迟、冷恢复时间，
扩班前优先迁至 NAS/数据库或实现并验证专用的日志归档工具。
128 MiB 是单次未压缩持久化载荷的默认保护上限，不代表实际租户容量或吞吐保证。

每套原系统仅有一个 teacher 账号；酒店有多班级，餐饮使用统一注册口令。
1000 学生/50 老师是后续目标规模，本次仅验证 10 班、10 人并发模拟流程；
未增加独立教师账号、教师授课权限，也未做 1000 人并发负载测试。

## 5. 导出到 NAS，保留现有数据

切换 `STORAGE_BACKEND` 不会自动同步两个后端。空 NAS 目录会产生新系统，
需要保留飞书试点数据时按以下步骤停写导出：

1. 停止所有本地/FC 写入进程。
2. 使用同一组飞书配置与密钥，在仓库根目录导出到一个**不存在的新目录**：

```bash
node --env-file=.env scripts/export-feishu.cjs --stopped-writer ./data/nas-export-20261020
```

3. 工具只读取飞书，生成两套 SQLite 和私密初始化配置；成功后包含 `EXPORT_COMPLETE`。
   如果报错，输出目录属于不完整导出，不可部署。重新尝试必须选择另一个新目录。
4. 安全传输导出目录的内容到空的 NAS 数据目录，验证权限与 SQLite 完整性。
5. 设置 `STORAGE_BACKEND=nas`、`DATA_DIR=/mnt/teaching/data`、`SQLITE_JOURNAL_MODE=DELETE`，
   按 NAS 说明启动并验证已有账号、成绩和课堂记录。
6. 保留原飞书数据及密钥作为停写时的备份，不再向旧飞书部署写入。

导出包含账户哈希、会话与课堂数据，不能放在公开下载目录或 Git 仓库。
NAS 回到飞书暂未提供自动迁移；不要直接切换并期望读取 NAS 中的新数据。
数据模型升级也需要显式迁移，目前恢复时遇到不兼容 schema 会拒绝启动。
